# QrDrop

**用一块屏幕和一个摄像头传文件。**

发送端把文件编码成滚动播放的二维码序列，接收端用手机摄像头对着屏幕连续扫描，还原出原始文件。全程不碰网络、蓝牙、配对，也不需要 U 盘——只要对方能看见你的屏幕，文件就能过去。

适用于物理隔离网络、禁止外接存储的机房、临时借用的陌生电脑，以及任何"能看见但连不上"的场景。

## 特性

同类的"二维码传文件"工具大多止步于"把文件切片、依次显示、扫完拉倒"——中途一旦断掉、漏帧、想调速，就只能从头再来。QrDrop 的设计重心正是这些真实场景里绕不过去的问题。

| 特性 | 介绍 |
|---|---|
| [免补帧](#免补帧) | 可以在任意发送进度下开始扫码，且不需要补缺 |
| [进度保存与断点续传](#进度保存与断点续传) | 两端各自存盘，关掉重开从上次位置继续 |
| [实时切换速率与带宽](#实时切换速率与带宽进度不作废) | 传输途中随时调快慢与密度，已接收数据依然可用，进度不作废 |
| [多文件并行传输](#多文件并行传输) | 多个文件的二维码互相独立不混淆 |
| [进度共享](#进度共享跨设备接力) | 接收进度可导出分享，换台设备接着扫 |
| [低功耗](#低功耗) | 帧率上限可调 + 双识别引擎，按需分配算力 |
| [老旧浏览器支持](#支持老旧浏览器ie10--android-4--ios-6) | 发送端一个 HTML 文件，IE10 / Android 4 也能跑 |

### 免补帧

传统分片方案给每一片编号，接收端扫完发现缺了第 37、112、409 片，就得回头让发送端把这几片重新显示一遍——而单向光学信道下接收端根本没法告诉发送端缺了哪些，只能靠人工补，或者干脆整个重播一轮。

QrDrop 允许漏任意帧，只需**收够足够数量就能还原，与具体收到了哪些数据块无关**。没有"缺块"的问题，不需要补帧、不需要重播轮次、不需要任何回传通道。

### 进度保存与断点续传

**两端各自持久化，互不依赖。**

发送端的播放游标以 sessionId 为键存盘（Java版在 `~/.qrdrop/playback/`，Web 版在 localStorage），关掉程序、重启电脑，重新选中同一个文件会推导出同一个 sessionId，从上次的位置接着往下发，而不是从头开始。

接收端把每个会话的已收数据以二进制格式自动落盘，App 切后台、被系统杀掉、手机重启，下次打开自动恢复，进度条停在哪就从哪继续。

传一个大文件传到一半没电了？充上电接着扫，之前的都还在。

### 实时切换速率与带宽，进度不作废

传输途中两个旋钮都能随时动，且**接收端已经收到的数据全部继续有效**：

- **速率**——显示间隔，快慢随时调
- **带宽**——二维码档位，即单帧承载的数据量

这一点比听上去难得多。档位一变，二维码的版本、容量、每帧块数全变了，多数方案到这里只能重开会话。QrDrop 把**源块大小与二维码档位彻底解耦**：块大小在会话开始时由文件大小决定并锁定，换档只改变"每帧塞几个块"，块本身的定义不变，所以旧块和新块可以混着用。

实际意义：现场光线变差、手抖、距离变远导致识别率掉下来，直接降一档继续，不用从头再传。条件变好了就升档提速。

### 多文件并行传输

发送端支持多选，每个文件是一个独立会话，各有各的参数与游标。接收端同时维护多个会话，靠帧头里的 sessionId 自动归类——**几个文件的二维码交替扫、混着扫都不会串**，各自的进度条独立推进。

### 进度共享（跨设备接力）

接收端可以把当前的接收进度**导出成一个文件分享出去**，另一台设备导入后从这个进度接着扫。

导出包含全部未完成的会话，格式与本地存盘格式一致。用途很直接：你的手机快没电了，把进度发给同事的手机接着收；或者几台设备分头扫同一块屏幕，最后把进度汇总到一起。

### 低功耗

连续扫描二维码是持续的相机采集加图像识别，是明确的发热大户。QrDrop 在两个层面控制：

- **帧率上限可调**（5–30 fps）。超出设定频率的相机回调**直接丢弃**，不进入识别环节——硬件给 30 fps，但识别只做 20 次，功耗按需分配。
- **双识别引擎可选**。Vision 逐帧跑 ML 推理，识别力强；AVFoundation 在相机采集管线内部完成检测，功耗明显更低，适合长时间高帧率扫描。

再加上重复载荷的短路判定：同一个二维码被连续扫到多次时，后续几次在最外层就被识别为重复而直接跳过，不做任何解码工作。

### 支持老旧浏览器（IE10 / Android 4 / iOS 6）

Web 发送端是**一个双击就能打开的 HTML 文件**，零依赖、零构建、零安装——不需要 Node，不需要包管理器，不需要联网拉 CDN。

更关键的是它**只用 ES5 语法**：不用 Promise、fetch、crypto.subtle、TextEncoder、BigInt、箭头函数、let。连 QR 编码器都是自己实现的（字节模式 / ECC=L / V1–40），不依赖任何第三方库。缺 `Math.imul` 时自动降级成手工半字乘法，文件导出在 IE10/11 走 `msSaveBlob`。

结果是 IE10、Android 4.0 原生浏览器、iOS 6 Safari 都能跑。这正是物理隔离环境里最常见的机器状况——那些机房里的电脑往往就是十年前的系统，装不了新软件，也连不上网去下载。能力不足的浏览器会得到明确提示，而不是白屏。

### 紧凑的帧格式

仅20 字节二进制帧头承载 sessionId / 块大小 / 总块数 / 每帧块数 / 起始块号 / CRC32，文件名等元信息内嵌进流层而不是每帧重复。单帧有效载荷率 **99.2%**（V40 档），相比旧版的 JSON + Base64 封装（约 69%）提升近一半——同样的屏幕、同样的时间，多传 40% 以上的数据。

编码块参与异或的源块由两端用同一个伪随机数生成器从块号推导，完全不占载荷。

## 怎么用

### 一、启动发送端

**Web 版**（推荐，任何设备都能用）：双击 `sender/web/index.html`，浏览器里选择要传的文件即可。

**桌面版**（Java，支持流层压缩，只依赖 ZXing core 2.3.0）：

```bash
mvn -o -f sender/java/pom.xml clean package
java -cp sender/java/target/classes:<zxing core jar> org.file.qrcode.SenderApp
```

启动后点「选择文件」，一个文件就是一个会话。

**单文件精简版**（`sender/java-min/QrDropSender.java`，整套协议 + 界面就一个文件，只依赖 ZXing core）：

```bash
javac -encoding UTF-8 -cp core-2.3.0.jar sender/java-min/QrDropSender.java
java -cp core-2.3.0.jar:sender/java-min QrDropSender                      # 图形界面
java -cp core-2.3.0.jar:sender/java-min QrDropSender --dump 待传文件 out.vddump 2   # 无界面导出帧转储
```

帧字节与完整版逐位相同（已对拍），区别只是不做播放状态持久化。

### 二、对焦

选好文件后屏幕上先静止显示一帧二维码，用来让接收端从容取景、对准、合焦。建议此时点「全屏」（纯白背景、无边框），识别率明显更好，ESC 退出全屏。

### 三、开始播放，用手机扫

发送端点播放，二维码开始滚动。接收端打开 QrDrop iOS App，点"摄像头扫描"，对准屏幕即可。进度条会实时显示收了多少。

收满之后在 App 里点击该会话，还原出文件，然后通过系统分享保存或转发到任何地方。

### 中途要停？

直接关就行，两端都不需要做任何"保存"操作。下次发送端重新选中同一个文件、接收端重新打开 App，进度都还在，接着传。

要换台设备接着收，在接收端导出进度文件发过去，另一台导入后继续扫。

### 调参建议

发送端有两个旋钮，配合接收端的扫描帧率使用：

| 旋钮 | 建议值 | 说明 |
|---|---|---|
| **显示间隔** | 75–100 ms | 太快会超出摄像头的采样能力，接收端会漏帧 |
| **档位** | 从中间档试起 | 档位越高单帧信息越多，但对屏幕素质、距离、对焦要求也越高 |

接收端可调分辨率（720p / 1080p，默认 720p）与帧率上限（5–30 fps，默认 20 fps）。经验法则：**显示间隔 × 帧率 / 1000 ≥ 2.5**，即每个二维码至少被扫到 2.5 次；并尽量避开整数比，防止相位锁定导致某些帧永远扫不到。

传大文件时如果屏幕素质好、距离近，可以提高档位；反之如果进度推进缓慢，先降档位、再放慢显示间隔。

## 项目结构

```
QrDrop/
├── protocol/     协议契约、Python 参考实现与跨语言测试向量
├── sender/java/  桌面发送端（Java Swing）
├── sender/web/   Web 发送端（纯原生 HTML + JS，零依赖）
└── receiver/     接收端（iOS，SwiftUI + Vision）
```

三端共用一份协议，逐位比对同一套测试向量，任意发送端都能配任意接收端。
